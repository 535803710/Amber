# Amber 产品方向讨论结论（2026-08-06）

> 状态：本次产品判断已同步到《琥珀计划》和 README。本文保留讨论依据，不代表拟议能力已经实现。

## 1. 出发点

Amber 最初要解决的问题很明确：TClaw 无法直接读取本地 Git 仓库和工作区，因此需要把 AI 实际完成的编码工作及 Git 提交沉淀下来，让 TClaw 知道研发过程中做了什么。

后续扩展必须继续服务于这个问题，不能为了覆盖完整研发流程而增加额外负担。对外表达优先使用“AI 编码工作记录”或“研发事实”，不以“AI 编码量”作为产品定位，避免被理解为按行数统计工作量或用于个人绩效。

## 2. 产品定位

Amber 的核心定位是：把 AI 修改和 Git 提交转换为可查询、可追溯、可被下一次研发任务使用的事实。

Amber 不负责成为完整的研发管理平台，也不独立给出最终研发判断。它的价值在于补足 TClaw 看不到真实代码的缺口，并把历史证据提供给能够读取当前代码、Git 和测试结果的 IDE Agent。

## 3. 当前主线

原五阶段路线暂不继续按顺序扩张，当前收敛为三层：

| 层级 | 内容 | 状态 |
| --- | --- | --- |
| 研发事实采集 | AI 修改、Git 提交、可靠投递、健康监控 | 基础能力已具备 |
| MCP 证据服务 | 从历史中返回与当前任务真正相关的事实和来源 | 当前重点，仍需验证和改善 |
| IDE 上下文恢复 | IDE Agent 结合当前代码、Git、测试与 MCP 历史恢复研发现场 | 下一步验证 |

现阶段不以“阶段数量”衡量进展，而以历史证据是否真正减少重复排查、遗漏和返工来判断是否继续投入。

## 4. 组件边界

- TClaw/Amber MCP 提供历史证据，但拿不到实时工作区、未提交代码和测试状态，不能独立保证恢复结果准确。
- MCP 的输出是参考证据，不是当前事实，也不能覆盖当前用户需求、代码、Git 和测试结果。
- IDE Agent 负责读取真实代码和当前状态，结合 MCP 历史后形成最终判断。
- 如果历史记录与当前事实冲突，以当前事实为准，并明确标出冲突或未知项。

## 5. 暂不进入主路线的能力

以下能力先放入机会池，不作为当前承诺阶段：

- 完整的 AI 变更验收和 Review 流程；
- 主动遗留雷达；
- 团队知识地图；
- 发布风险、故障反查和回滚建议；
- 自动提炼 Skill；
- 覆盖研发全生命周期的流程编排。

目前内部需求通常只有一句话，并由一个人完成分析、实现和验证；只有部分外部需求会提供需求文档、用户故事和原型。缺少稳定、统一的上游产物时，建设一套通用的变更验收流程容易增加补材料和维护规则的负担，ROI 暂不明确。

只有出现稳定、重复且代价明确的真实问题，并能证明收益高于维护成本时，才考虑选择性实现。尤其是风险检查，应尽量按需触发、低噪音、接近零人工维护。

## 6. MCP 输出问题与处理结果

原 MCP 输出偏原始和杂乱，检索过程、审计字段和证据内容混在一起，增加了人和 AI 的判断负担。

现已通过 v2 输出契约完成第一轮收敛：

- 普通任务默认返回 3 条强相关 AI 修改证据；历史演变、最终决定、重构、迁移或删除等任务会在一次调用内升级为 `compact + 8`，最多可显式请求 10 条；
- 每条默认包含用户需求、修改结果、完成时间和涉及文件；自动升级结果会在 `retrieval` 中说明实际密度、上限和原因；
- Git 提交只作为强关联 AI 修改的嵌套补充，不替代 IDE 的 Git 查询；
- `compact` 和 `full` 可在默认证据不足时按需使用；历史演变题由服务端自动提升到 `compact`；
- MCP 不生成决定、风险和最终结论，由 IDE Agent 结合当前代码、Git 和测试判断。

飞书失败或本地回退只返回简短状态，不再把完整错误和警告交给模型。后续重点转为真实任务中的相关性和信息密度验证。

## 7. 信息记录边界

- 保持现有自动采集边界：只有实际发生文件改动时，才通过 Webhook 记录 AI 修改事件。
- 不自动记录完整对话、探索过程、犹豫和未定型想法。
- 少量重要决定暂时直接写入仓库文档，由 IDE Agent 结合当前代码核验。
- 不在飞书新增决策记录表，也不把决策混入现有 AI 修改记录表。
- 研发记录不进入个人工作量统计或排名。

这样既能保留重要上下文，也能降低监控感和绩效压力。

## 8. 决策记录能力（暂缓建设）

当前不新增决策记录表，不复用 AI 修改记录表，也不实现 `amber_record_decision`。现有 `amber_get_task_context` 继续保持只读。

主要原因是决策表达的是当时意图，具体实现可能尚未完成、已经改变或被后续决定替代。如果缺少状态、适用范围、关联提交、废止关系和当前代码核验，决策记录会被误当作事实，给 MCP 增加更多噪音。

将决策直接放入 AI 修改记录表还会混淆“已经发生的修改”和“尚未验证的意图”，影响检索、统计和理解。为解决这些问题而建设完整生命周期机制，当前投入产出比不足。

因此该能力不列为近期待办。只有未来真实任务反复因缺少决策记录而产生明显损失时，才重新评估。

## 9. 后续验证事项

- 用哪些真实案例和指标验证历史复用的 ROI。

现有《琥珀计划》已经按本次产品方向和 MCP v2 输出契约完成更新。在 ROI 得到验证前，不启动机会池中的重型能力。
