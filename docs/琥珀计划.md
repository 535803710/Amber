# Amber（琥珀计划）

> 代码奔向未来，记忆却散落在身后。  
> 我们将每一次人与 AI 的相遇封存在时间里，让后来者不必再从遗忘出发。

## 1. 项目目标

Amber 希望把一次性的 AI 研发协作，转化为可查询、可关联、可继续使用的研发事实。

在 AI Native Loop 中，需求、AI 对话、工作区修改和 Git 提交通常分散在不同工具与时间点。Git 能保存最终代码，但不能完整说明为什么修改、AI 做了什么，以及一次修改是否已经提交。Amber 负责采集并沉淀这些事实，为 TClaw 和 IDE Agent 后续查询、关联与恢复研发现场提供数据基础。

核心价值是让历史事实进入下一次研发任务，减少上下文丢失、遗漏、返工和故障处理成本。

Amber 记录的是“AI 编码工作”和“研发事实”，不是用于衡量个人绩效的“AI 编码量”。它也不建设完整研发管理平台，不要求使用者为了流程补充额外材料。

## 2. 整体链路

```text
用户需求
  → Cursor / ChatGPT 执行
  → Amber 采集 AI 修改事件
  → Git commit 固化代码历史
  → Amber 采集 Git 提交事件
  → 本地 Outbox 可靠投递
  → 飞书多维表格沉淀
  → Amber MCP 查询相关历史证据
  → IDE Agent 结合当前代码、Git 和测试恢复现场
```

各层保留最擅长的事实：

| 链路节点 | 沉淀内容 | 作用 |
| --- | --- | --- |
| Cursor / ChatGPT | 用户需求、AI 结果摘要、实际涉及文件 | 保留修改意图和执行结果 |
| Git | commit、分支、作者、文件和增删统计 | 确认哪些修改进入正式代码历史 |
| Amber | 标准化事件、本地队列、投递状态 | 连接不同工具并保证可靠采集 |
| 飞书 | 结构化记录、权限和团队可见性 | 提供稳定的数据入口 |
| TClaw / Amber MCP | 跨会话、跨工具、跨时间关联 | 提供与当前任务相关的历史证据 |
| IDE Agent | 当前需求、代码、Git、测试和历史证据 | 形成最终上下文和研发判断 |

## 3. 核心事件

### 3.1 AI 修改事件

AI 修改事件描述一次 Agent 轮次实际造成的工作区变化。

采集过程：

```text
任务开始
  → 使用临时 Git index 捕获工作区 baseline
  → 任务完成后再次捕获工作区 tree
  → 比较两棵 tree
  → 汇总新增、修改、删除、重命名文件及增删行
  → 写入本地 Outbox
  → Worker 投递飞书
```

主要字段包括：

- 工具来源、项目、仓库路径和分支；
- 会话 ID、轮次 ID、事件 ID；
- 用户需求摘要和 AI 结果摘要；
- 修改文件、文件数量、增加行和删除行；
- 结果状态和采集质量；
- baseline tree 与结果 tree。

只有工作区实际发生变化时才生成事件。纯问答、分析或最终没有文件变化的轮次不会写入飞书。

### 3.2 Git 提交事件

Git 提交事件描述一次代码历史固化结果。

Amber 轮询 `COMMIT_RECORD_SCAN_ROOTS` 配置目录下指定深度内的 Git 仓库和本地分支，支持用分号配置多个绝对路径。未配置时不扫描。首次发现仓库时只建立基线，之后发现新增 commit 才生成事件，避免将历史提交批量回灌。

主要字段包括：

- 项目、仓库路径、远端地址和分支；
- commit SHA、父提交、作者、提交时间；
- 标题、说明和提交类型；
- 修改文件、文件数量、增加行和删除行；
- 最近时间窗口内修改相同文件的 AI 事件 ID。

监听目标为本地 `git commit`；`git push` 不生成事件。同一次提交只应生成一条记录。

## 4. 当前已经具备的能力

截至 2026-08-06，Amber 已具备以下基础闭环：

- Cursor AI 修改记录的自动采集与飞书投递；
- Codex/ChatGPT 用户级 Hook 配置、采集逻辑和模拟链路验证；
- 新增、修改、删除、重命名、暂存和未跟踪文件识别；
- Windows 中文 Hook 载荷和 Git 中文文件名兼容；
- Git 仓库轮询、分支基线、新 commit 识别和历史回灌保护；
- AI 修改事件与 Git commit 的文件、时间和事件 ID 关联基础；
- AI 与 Git 两类独立本地 Outbox；
- `pending → processing → sent/failed` 原子抢占，避免多 Worker 重复发送；
- 失败重试、失败队列重放和超时 processing 恢复；
- 本地只读记录页、配置状态和队列状态展示；
- `core` 档位常驻 AI/Git 采集与健康监控，`full` 档位按需增加 Windows 通知和 UI 提示监听；
- 独立健康监控、异常分级、告警去重、恢复通知和残留状态归档；
- TClaw 已能读取飞书记录，并完成按时间、项目和分支汇总代码进度的初步验证；
- 只读 `amber_get_task_context` MCP v2：普通任务默认返回 3 条强相关 AI 修改证据；历史演变、最终决定、重构、迁移或删除等任务会在一次调用内升级为 `compact + 8`，最多可显式请求 10 条；
- `minimal` 证据包含完成时间；自动升级结果会返回时间顺序，并在 `retrieval` 中说明实际密度、上限和升级原因；
- Git 提交只作为强关联修改的嵌套补充，无强匹配时返回空证据，飞书不可用时回退目标仓库本地记录。

## 5. 数据与安全边界

Amber 默认采集研发元数据，不保存完整源码和完整 diff。

- Webhook URL、Token 等真实凭证只保存在本机 `.env.local`；
- 本地队列、日志、baseline 和密钥不进入 Git；
- 飞书记录包含需求和 AI 回复摘要，仍可能出现业务信息；
- 飞书表格需要限制访问权限，并定义数据保留周期；
- 事件 ID 应作为飞书侧幂等去重依据；
- 记录用于研发上下文和工程改进，不应直接用于个人绩效排名；
- 推广时应公开采集字段、用途、查看权限，以及暂停或退出方式。
- 自动采集继续以“实际发生文件修改”为边界，不记录完整对话、探索过程和未定型想法；
- 少量重要决定暂时写入仓库文档，由 IDE Agent 结合当前代码核验；不新增决策表，也不混入 AI 修改记录表。

## 6. 当前投入优先级

当前不再按完整研发流程扩张，而是按能否产生可验证价值确定投入顺序。

| 优先级 | 能力 | 核心价值 | 当前状态 |
| --- | --- | --- | --- |
| 1 | 研发事实采集 | 可靠记录 AI 修改和 Git 提交 | 基础能力已具备 |
| 2 | MCP 证据服务 | 准确返回相关历史，减少重复排查和遗漏 | v2 已收敛输出，进入真实任务验证 |
| 3 | IDE 上下文恢复 | 结合当前代码、Git、测试和历史证据恢复现场 | 下一步验证 |

日报和修改行数只作为辅助信息，不用于个人绩效评价。后续投入以真实任务中节省时间、避免遗漏和减少返工为依据。

## 7. 当前路线

### 第一层：研发事实采集（已具备）

保持 AI 修改、Git 提交、可靠投递、健康监控和查询入口稳定。只有实际文件变化才生成 AI 修改事件，不扩大到完整对话和思考过程。

### 第二层：MCP 证据服务（当前重点）

- v2 默认只返回最多 3 条需求、结果和文件，减少无关字段；
- AI 修改作为主证据，Git 提交仅作为强关联的嵌套补充；
- MCP 只提供历史证据，不生成决定、风险和最终结论；
- 保持“历史只是证据，当前需求、代码、Git 和测试优先”的边界；
- 用真实任务验证是否减少重复排查、遗漏和返工。

### 第三层：IDE 上下文恢复（下一步验证）

- IDE Agent 读取当前工作区、Git、代码和测试；
- 需要历史时调用 Amber MCP，获取相关证据；
- 由 IDE Agent 处理历史与当前事实的冲突并形成最终结论；
- Amber/TClaw 不在缺少真实代码的情况下独立承诺恢复准确性。

### 机会池：暂不承诺

- 完整的 AI 变更验收和 Review 流程；
- 主动遗留雷达；
- 团队知识地图；
- 发布风险、故障反查和回滚建议；
- 自动提炼 Skill；
- 覆盖研发全生命周期的流程编排。

这些能力只有在出现稳定、重复且代价明确的问题，并能证明收益高于维护成本时才选择性建设。内部需求通常只有一句话且由一个人完成，缺少统一上游产物时，不建设要求补材料的通用验收流程。

## 8. 当前限制与风险

| 风险 | 当前状态 | 应对方向 |
| --- | --- | --- |
| ChatGPT 会话工作区失效 | 项目目录改名后，旧会话仍绑定旧 cwd，Hook 无法启动 | 改名后重新打开 Amber 工作区并新建会话 |
| ChatGPT Hook 生命周期 | 是否执行取决于客户端加载、信任状态和会话生命周期 | 增加真实新增、修改、删除回归验收和状态提示 |
| Cursor 日志依赖 | 中文回复恢复依赖 Cursor 本地 UTF-8 Hook 日志 | Cursor 升级后执行中文回归测试并保留降级标记 |
| 并发修改 | 多个 Agent 同时修改同一仓库时归因可能不精确 | 标记 `concurrent_risk`，后续增强关联策略 |
| 扫描覆盖范围 | 仅扫描 `COMMIT_RECORD_SCAN_ROOTS` 配置的目录，未配置时不扫描 | 在控制台或 `.env.local` 明确配置实际项目目录 |
| 敏感信息 | 需求和结果摘要可能包含内部信息 | 权限、脱敏、保留周期和审计治理 |
| 监控感受 | 成员可能误解为个人工作量追踪 | 明确用途、字段、权限和退出机制 |
| MCP 输出噪音 | v2 已收敛为默认 Top 3 最小证据 | 通过真实任务继续检查相关性和信息密度 |
| 恢复准确性 | TClaw/MCP 无法读取实时工作区和测试状态 | 由 IDE Agent 结合当前事实形成最终判断 |

## 9. 当前判断与近期重点

采集链路和可观测性已经完成，Amber 当前进入“MCP 证据服务验证”阶段。近期重点为：

1. 在真实研发任务中验证 MCP v2 的 Top 3 证据是否足够且相关；
2. 验证“IDE Agent + 当前代码/Git/测试 + MCP 历史”的恢复方式；
3. 记录历史证据实际节省时间、避免遗漏或减少返工的案例；
4. 在 ROI 得到证明前，不启动机会池中的重型能力。

决策记录能力暂缓建设：不新增决策表、不混入 AI 修改记录表，也不实现 `amber_record_decision`。现有 `amber_get_task_context` 保持只读，避免未实施或已过期的决定被误当作当前事实。详细讨论见 [产品方向讨论结论（2026-08-06）](产品方向讨论结论-2026-08-06.md)。
