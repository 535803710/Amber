# Amber（琥珀计划）

> 代码奔向未来，记忆却散落在身后。  
> 我们将每一次人与 AI 的相遇封存在时间里，让后来者不必再从遗忘出发。

## 1. 项目目标

Amber 希望把一次性的 AI 研发协作，转化为可查询、可关联、可继续使用的研发事实。

在 AI Native Loop 中，需求、AI 对话、工作区修改和 Git 提交通常分散在不同工具与时间点。Git 能保存最终代码，但不能完整说明为什么修改、AI 做了什么，以及一次修改是否已经提交。Amber 负责采集并沉淀这些事实，为飞书中的团队共享以及 TClaw 后续查询、关联和行动提供数据基础。

核心价值不是积累更多记录，而是让历史事实进入下一次研发任务，减少上下文丢失、遗漏和重复沟通。

## 2. 整体链路

```text
用户需求
  → Cursor / ChatGPT 执行
  → Amber 采集 AI 修改事件
  → Git commit 固化代码历史
  → Amber 采集 Git 提交事件
  → 本地 Outbox 可靠投递
  → 飞书多维表格沉淀
  → TClaw 查询、关联、总结和提醒
  → 反哺下一次研发任务
```

各层保留最擅长的事实：

| 链路节点 | 沉淀内容 | 作用 |
| --- | --- | --- |
| Cursor / ChatGPT | 用户需求、AI 结果摘要、实际涉及文件 | 保留修改意图和执行结果 |
| Git | commit、分支、作者、文件和增删统计 | 确认哪些修改进入正式代码历史 |
| Amber | 标准化事件、本地队列、投递状态 | 连接不同工具并保证可靠采集 |
| 飞书 | 结构化记录、权限和团队可见性 | 提供稳定的数据入口 |
| TClaw | 跨会话、跨工具、跨时间关联 | 生成可执行的上下文、总结和提醒 |

## 3. 核心事件

### 3.1 AI 修改事件

AI 修改事件描述一次 Agent 轮次实际造成的工作区变化。

采集过程：

```text
任务开始
  → 使用临时 Git index 捕获工作区 baseline
  → 任务完成后再次捕获工作区 tree
  → 比较两棵 tree
  → 汇总新增、修改、删除、重命名文件及增删行
  → 写入本地 Outbox
  → Worker 投递飞书
```

主要字段包括：

- 工具来源、项目、仓库路径和分支；
- 会话 ID、轮次 ID、事件 ID；
- 用户需求摘要和 AI 结果摘要；
- 修改文件、文件数量、增加行和删除行；
- 结果状态和采集质量；
- baseline tree 与结果 tree。

只有工作区实际发生变化时才生成事件。纯问答、分析或最终没有文件变化的轮次不会写入飞书。

### 3.2 Git 提交事件

Git 提交事件描述一次代码历史固化结果。

Amber 轮询 `COMMIT_RECORD_SCAN_ROOTS` 配置目录下指定深度内的 Git 仓库和本地分支，支持用分号配置多个绝对路径。未配置时不扫描。首次发现仓库时只建立基线，之后发现新增 commit 才生成事件，避免将历史提交批量回灌。

主要字段包括：

- 项目、仓库路径、远端地址和分支；
- commit SHA、父提交、作者、提交时间；
- 标题、说明和提交类型；
- 修改文件、文件数量、增加行和删除行；
- 最近时间窗口内修改相同文件的 AI 事件 ID。

监听目标是本地 `git commit`，不是 `git push`。同一次提交只应生成一条记录。

## 4. 当前已经具备的能力

截至 2026-08-01，Amber 已具备以下基础闭环：

- Cursor AI 修改记录的自动采集与飞书投递；
- Codex/ChatGPT 用户级 Hook 配置、采集逻辑和模拟链路验证；
- 新增、修改、删除、重命名、暂存和未跟踪文件识别；
- Windows 中文 Hook 载荷和 Git 中文文件名兼容；
- Git 仓库轮询、分支基线、新 commit 识别和历史回灌保护；
- AI 修改事件与 Git commit 的文件、时间和事件 ID 关联基础；
- AI 与 Git 两类独立本地 Outbox；
- `pending → processing → sent/failed` 原子抢占，避免多 Worker 重复发送；
- 失败重试、失败队列重放和超时 processing 恢复；
- 本地只读记录页、配置状态和队列状态展示；
- `watch:all` 常驻运行及 Windows 开机启动支持。

## 5. 数据与安全边界

Amber 默认采集研发元数据，不保存完整源码和完整 diff。

- Webhook URL、Token 等真实凭证只保存在本机 `.env.local`；
- 本地队列、日志、baseline 和密钥不进入 Git；
- 飞书记录包含需求和 AI 回复摘要，仍可能出现业务信息；
- 飞书表格需要限制访问权限，并定义数据保留周期；
- 事件 ID 应作为飞书侧幂等去重依据；
- 记录用于研发上下文和工程改进，不应直接用于个人绩效排名；
- 推广时应公开采集字段、用途、查看权限，以及暂停或退出方式。

## 6. TClaw 可继续建设的能力

Amber 当前重点是提供可靠事实，TClaw 负责把事实转化为团队能力。

| 能力方向 | 场景 | 直接产出 |
| --- | --- | --- |
| 记录检索与汇总 | 按项目、时间、文件查询 AI 修改和 commit | 每日摘要、个人回顾、项目交接材料 |
| 上下文关联与解释 | 关联相同仓库、文件和时间窗口内的事件 | commit 背景和修改原因说明 |
| 异常与遗漏识别 | AI 已修改但长期没有 commit | 遗漏提醒和待处理清单 |
| 变更风险识别 | 大量删除、配置修改、高频返工 | 风险提示、Review 和测试建议 |
| 历史经验沉淀 | 分析模块修改历史和常见返工路径 | 任务前置上下文、经验复用和故障追溯 |

建议按“查询 → 关联 → 提醒 → 经验复用”的顺序逐步落地，先验证数据质量和团队价值，再增加主动干预。

## 7. 当前限制与风险

| 风险 | 当前状态 | 应对方向 |
| --- | --- | --- |
| ChatGPT 会话工作区失效 | 项目目录改名后，旧会话仍绑定旧 cwd，Hook 无法启动 | 改名后重新打开 Amber 工作区并新建会话 |
| ChatGPT Hook 生命周期 | 是否执行取决于客户端加载、信任状态和会话生命周期 | 增加真实新增、修改、删除回归验收和状态提示 |
| Cursor 日志依赖 | 中文回复恢复依赖 Cursor 本地 UTF-8 Hook 日志 | Cursor 升级后执行中文回归测试并保留降级标记 |
| 并发修改 | 多个 Agent 同时修改同一仓库时归因可能不精确 | 标记 `concurrent_risk`，后续增强关联策略 |
| 扫描覆盖范围 | Git 默认只覆盖 `D:/project` 及配置深度内的本地仓库 | 在安装说明中明确范围并支持可配置目录 |
| 敏感信息 | 需求和结果摘要可能包含内部信息 | 权限、脱敏、保留周期和审计治理 |
| 监控感受 | 成员可能误解为个人工作量追踪 | 明确用途、字段、权限和退出机制 |

## 8. 阶段判断

Amber 已经从“概念验证”进入“可试点的采集基础设施”阶段。AI 修改事件、Git 提交事件、本地可靠队列和飞书写入已形成基础闭环；原子抢占、Git 历史回灌保护等关键可靠性问题已经修复。

下一阶段不应继续无限扩展采集字段，而应重点完成：

1. Cursor、ChatGPT、Git commit 三条真实链路的持续验收；
2. 采集成功率、投递延迟、重复率和失败恢复的可观测性；
3. TClaw 最小查询与关联闭环；
4. 小范围试点中的权限、保留周期和团队信任机制；
5. 用实际节省的检索、交接和遗漏处理时间衡量价值。

只有当这些记录能被 TClaw 在后续任务中稳定调用，并实际减少重复检索、遗漏和沟通成本时，琥珀计划才真正完成了从“保存记录”到“形成研发记忆”的转变。
